# Replay fixtures (S46)

Recorded request/response pairs, sliced out of a journal so a proof can replay real
replies instead of invented ones. Nothing here is hand-written: every file is
regenerated by its slicer, and every entry carries the journal `line` it came from.

## Reproduce

```bash
python3 spacemolt/proofs/fixtures/slice_gameplay.py \
    spacemolt/runtime/gameplay.jsonl spacemolt/proofs/fixtures/c23-replay.json

python3 spacemolt/proofs/fixtures/slice_bridge.py \
    ~/.hermes/profiles/kvothe/spacemolt/runtime/gameplay.jsonl \
    spacemolt/proofs/fixtures
```

## The two journals are not the same shape

The first attempt journalled one raw game command per line. The bridge journals its
own protocol — `{at, request:{id,action,params}, response:{id,ok,result|error}}` —
plus its own `chain`, `rest` and `reflection` events. Raw game replies survive in the
bridge journal only inside a ported-runner result, under `result.actions[]`. That is
the `game` section of a fixture; `bridge` is the protocol layer.

## Scrubbing

As `c23-replay.json`: other players' names and ids, the pilot's own id and username,
and the human-readable `result` string (nothing reads it). Bulk nothing reads —
station facility lists and descriptions, market order books, skill boards — is
dropped so a fixture stays reviewable in a diff.

## Not in either journal

A successful `spacemolt/repair`, `spacemolt/get_tax_estimate` and `spacemolt/set_home`
were never sent in either journal. Their shapes remain unproved, and so does
`base.repair_price_per_hull`, which production reads (`bridge.ts`, `servicing.ts`)
and no recorded `get_base` carries.

`spacemolt/get_skills` and `spacemolt_shipping/profile` are in `c23-replay.json`
(2026-09-08); `get_skills` returns `skills` as a map keyed by skill id, not an array.
